# 采集与空间数据约定

## 采集顺序

先选一栋食堂，确认其官方名称、入口、实际楼层数，再拍每层整体平面图与窗口照片。多人分工时先分配稳定 ID，不能把照片编号或显示顺序当作窗口 ID。

当前目录中的“四五六”“民族+八九”“十一十二”只是采集分组，不表示已经核实共用一栋楼。真实建筑若分开，应创建多个 venue，并为原示例 ID 建迁移映射。

| 实体 | 必采信息                                                   | 可后补信息                     |
| ---- | ---------------------------------------------------------- | ------------------------------ |
| 场所 | venue_id、正式名称、建筑边界、坐标来源/坐标系、核实日期    | 开放时间、无障碍入口           |
| 楼层 | floor_id、venue_id、层号、宽深、原点、北向、layout_version | GLB 模型、墙/柱/楼梯多边形     |
| 窗口 | stall_id、floor_id、名称、x/z、宽深、rotation_y            | 类别、营业时间、营业状态       |
| 菜品 | dish_id、stall_id、名称、价格（分）、采集日期              | 简介、过敏原声明（以商家为准） |
| 照片 | 关联 ID、Key、拍摄授权、SHA-256、尺寸、字节数              | alt 文本、摄影者署名           |

`data/templates/` 提供 CSV 表头和一个示意行。JSON 完整演示可运行 `npm run data:export` 生成。更改示例数据后运行 `npm run data:validate`。

## 三套坐标，不可混用

- **校园图纸坐标 CAMPUS_PLAN_V2**：1280 × 1920，相对位置源于参考图，无地理精度；详见 CAMPUS_PLAN.md。旧 V1 坐标不可混用。
- **真实地理坐标**：采集时明确 WGS84 / GCJ-02 / 其他来源。MapLibre 通常接受 WGS84 经度、纬度；高德使用 GCJ-02。按提供方官方方法转换，保留原始坐标和来源，避免重复转换。
- **楼层局部坐标 LOCAL_METERS**：图纸中心是 `(0,0)`，X 向右，Z 向下，Y 为高度，米制。窗口前台面朝 +Z 为 0 弧度，旋转为绕 +Y 右手规则。窗口的旋转矩形必须落在楼层边界内。

每个实体绑定稳定 ID。未来 GLB 中节点名称可为 `stall:<stall_id>`，业务数据同时保存该 ID。导出模型时应用单位缩放，保证 1 unit = 1 m。建筑定位需保存地理锚点、米制局部原点、北向角、标定版本；不能把 glTF 顶点直接当经纬度。

当前无需地理配准。只有未来新增 GPS 等需求时才设计地理转换，不能把相对图纸单位解释为米或经纬度。

## 图片和模型

建议 Key：`venues/<venue_id>/<uuid>.webp` 或 `stalls/<stall_id>/<uuid>.webp`。禁止原始文件名直接作为路径；不允许 `..`、绝对路径、完整 URL。不可变 Key 能避免迁移时缓存错配。

先保留原图到私有采集目录，公开图删除 EXIF/GPS、处理可辨认人物授权、去除无关个人信息。建议展示图最长边 1600 px，缩略图 400 px，WebP；实际上传安全要求见 SECURITY.md。GLB 建议单栋压缩后不超过 5 MB，纹理按需要控制到 1K–2K；这是初始预算，要通过手机实测调整。

`npm run files:sync -- <源桶> <目标桶> copy` 保持同一 Key；`check` 下载比较内容，而非只比较 ETag（分片上传的 ETag 未必是 MD5）。数据库备份不会包含图片原始字节。
