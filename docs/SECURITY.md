# 安全边界与开放写入的条件

## Phase 0 已有保护

- 所有业务表开启 RLS；匿名角色默认无 schema 权限。`foodmap_reader` 只能读已发布的食堂及其楼层/窗口/可用菜品、维护状态。
- 用户、第三方身份、评论、评分、举报、审核记录、媒体均没有公开读策略，也没有客户端写策略。
- 只读 API 对非 GET/OPTIONS 返回 405；查询参数不能拼成 SQL。错误只返回通用代码，不把数据库连接和堆栈发送到浏览器。
- 数据库 FK、评分唯一约束、价格与评分范围、文件元数据格式保护基本一致性。
- 业务写触发器执行只读维护开关；仅表所有者/部署管理员能修改开关。普通 API 登录角色只有 reader 权限。
- `.env`、备份、私有数据与文件目录不进入版本库。所有 VITE_ 变量都是公开变量。

RLS 对表所有者和 BYPASSRLS/超级用户不生效。业务 API 不能长期使用这些角色；Compose 已创建独立的 `foodmap_api`，服务端查询额外 `SET LOCAL ROLE foodmap_reader`。维护触发器也不能阻止管理员刻意禁用触发器或 TRUNCATE，因此冻结流程需要限制运维写权限。

## Phase 2 开放用户功能前必须实现

| 功能      | 服务端要求                                                                  | 验证方式                                      |
| --------- | --------------------------------------------------------------------------- | --------------------------------------------- |
| 登录      | JWT 校验、业务身份映射、issuer/audience、过期处理；Cookie 方案配 CSRF       | 伪造/过期/其他项目 token 均拒绝               |
| 评论      | 用户只写自己的内容；长度限制；纯文本输出；pending 后审核                    | 改 user_id 无法冒用，未审核评论不公开         |
| 评分      | 1–5 整数，每用户每窗口唯一；原子 upsert；审核后聚合                         | 并发更新仍只有一条，拒绝越界值                |
| 上传      | 登录、配额、随机 Key、限制 10 MB；验证 magic bytes 和真实解码；最大像素限制 | 伪装 MIME、SVG/HTML、解压炸弹、超大尺寸拒绝   |
| 图片处理  | 删除 EXIF；重新编码为 JPEG/PNG/WebP；私有暂存；审核后发布                   | 未审核 Key 无法公开读；文件和元数据 hash 一致 |
| 审核/举报 | moderator/admin 服务端鉴权；审核操作事务与审计                              | 普通用户不能赋予自己角色或批准内容            |
| 防滥用    | 用户 + IP 双维度限流、上传/评价每日额度、异常告警                           | 429 + Retry-After；不可仅依赖前端节流         |
| 一致性    | 幂等提交键；先上传临时文件再登记元数据；失败补偿清理                        | 重试不重复、孤儿文件定期隔离                  |

初期可用 PostgreSQL 记录限流窗口，不因想象中的规模先加入 Redis。上传文件成功不代表业务发布成功：`pending → approved/rejected` 需由受信任服务端变更。公开服务需要数据库备份告警、磁盘容量告警、证书到期监测和真实恢复演练。

## 权限矩阵（目标设计）

游客只读 approved 目录/媒体/聚合评价；会员能提交和管理自己的内容；审核员能审查用户内容并处理举报；管理员能管理目录和角色。角色授权、举报详情和审计不公开。当前实现仅有第一阶段目录读权限，后续角色策略尚未启用。

## 秘密处理

前端只能持有公开配置和短时用户访问 token。Supabase service role、数据库 owner 密码、S3 密钥、SMTP 密码、JWT 私钥只进入服务器/CI secrets。公开仓库前检查 git 历史；若发现已提交密钥，应先吊销再清理历史，而不是仅删除文件。

Auth 备份含密码散列也属于敏感信息，应加密并限制访问。不要将备份恢复或迁移日志保存含明文 URL 的连接串。
