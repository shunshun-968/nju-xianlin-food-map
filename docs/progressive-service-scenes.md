# 呢喃小屋与逸夫楼渐进贴图加载

本次仅调整两个售卖点的加载生命周期，未改动照片文件、几何参数、UV、相机、灯光或最终材质参数。

## 修改文件

- `src/lib/scene-loading.ts`：模型模块与图片预取解耦。
- `src/lib/progressive-model-assets.ts`（新增）：模型独立队列、暂停/销毁、共享像素与 GPU 纹理替换。
- `src/lib/image-assets.ts`、`src/lib/scene-performance.ts`（新增）：下载、解码和场景阶段的开发性能记录。
- `src/components/ninan-hut-signage.ts`、`src/components/yifu-kiosk-signage.ts`：原几何/UV 上的占位与异步高清更新；原同步入口保留供离线工具和现有测试使用。
- `src/components/NinanHutModel.ts`、`src/components/YifuKioskModel.ts`：接入每模型独立资源队列。
- `src/components/MapScene.tsx`：两个场景的首帧、上传、离开和销毁流程；其他模型沿用原编译等待。
- `tests/progressive-model-assets.test.ts`、`tests/scene-loading.test.ts`（新增）及 `tests/photo-crop.test.ts`：慢网、失败、生命周期、GPU 释放、最终 UV/材质一致性回归。

`model-image-assets.ts` 的原资源清单和缓存入口继续复用，无需改动。

## 已核实的阻塞

原流程为：并行下载模块和全部照片 → 等待所有图片下载及 `image.decode()` → 准备标牌 → 创建模型 → 等待整个场景 `compileAsync()` → 开始渲染。

逸夫楼当前实际加载的 `b102-board-surface.jpg` 为 3,480,490 字节；另有西墙画及两个品牌 PNG。呢喃小屋加载早餐牌、饮品牌、东墙海报及两个品牌 PNG。任一失败或迟迟未完成，都会阻塞原来的模型准备。

## 新流程和资源所有权

模块与照片仍并行请求；模型准备只等待模块。模型以原几何和最终材质配置创建，照片暂用 1×1 底色，品牌图暂用透明像素。首帧只编译当前可见物体需要的着色器。实际提交首帧后，启动模型独立的贴图队列，每帧最多处理一次图片加工和上传。

所有上述照片和品牌资源均不再阻塞首次显示；每张照片独立完成。只有逸夫楼同一块品牌条自身需要同时拿到两个品牌 PNG，其他表面不等待它。无下载成功时保留简单底色，不生成或猜写招牌内容。

图片继续使用 `loadModelImage()` 的共享请求/解码缓存。重复海报和品牌图共享只读 `THREE.Source`，每个表面有独立可释放的 Texture 对象。切换高清前释放占位纹理的 GPU 分配，再为同一个材质引用的 Texture 绑定原始像素，保持色彩空间、各向异性过滤、裁切和 UV 不变。

离开场景暂停更新队列；网络任务继续服务共享缓存。重进恢复未完成项，失败项可以重试。模型销毁时取消 RAF/定时器、使旧回调失效并清空其材质引用，随后沿用原释放流程。完整加载的缓存模型重进不重复加工或上传照片。

其他食堂和南门餐车继续使用原准备与 `compileAsync()` 流程。

## 开发环境阶段记录

浏览器 Performance 面板或 `performance.getEntriesByType('measure')` 中筛选 `foodmap:`：

- `module-ready`：模型模块下载/执行完成，包括已缓存模块的情况。
- `image:download`、`image:decode`：单张图片的下载与显式解码等待；detail 含 URL。浏览器内部可能在 load 事件前已做部分解码，因此两者不是严格的网络/CPU 剖析。
- `model-create`：模型同步创建和模型内原有合批。
- `first-render-gpu`：首次 render 调用耗时，包括必要着色器准备及首帧提交，不等同于 GPU 硬件计时。
- `first-visible`：从本次场景激活开始至首次渲染提交，detail 含模型缓存状态。
- `texture-upload`：单次 `initTexture()` 调用耗时，不等同于 GPU 硬件计时。
- `hd-ready`：全部注册照片/品牌纹理加工上传完成；失败时记录 `hd-settled-with-errors` 和失败数量。

这些记录仅在开发环境启用。

## 本地验证（2026-10-29）

全量 `npm test` 256 项通过；`npm run build` 和 TypeScript 检查通过。构建只有现有的大 chunk 提示。

新增测试覆盖慢图片与快图片独立完成、每帧上传、共享下载、失败重试、退出/重进、销毁后的晚到回调、旧 GPU 分配释放、共享像素不重复失效。补充裁切测试确认渐进和同步路径的 UV 完全相同，替换后材质和几何对象不变，使用同一张已解码原图。

真实浏览器对照使用桌面 Edge 无头模式、SwiftShader 软件渲染、390×844 视口。每个相关图片请求人为延迟 8 秒；基线由当前 Git HEAD 的原文件提供，新版由当前工作树提供。以下为单次开发环境采样，计时从页面导航至场景可见，包含模块和应用启动，不能直接换算为真实手机加速比例。

| 逸夫楼 | 12.69 秒 | 5.11 秒 | 0 |

新版同步建模分别约 241/261 ms。软件渲染首帧仍耗时约 2.23/1.78 秒，较大的单张高清纹理上传仍可达约 0.51/0.59 秒；分帧调度避免集中上传，但不能消除单张照片上传本身的成本。本次没有缩小照片来掩盖这部分开销。

浏览器验证了两个场景重复进入、快速切换至另一场景/校园、冷加载中退出、单张图片失败后重进补齐，未出现页面运行错误；重复进入时模型缓存命中。呢喃早餐/午餐/晚餐、逸夫夜景及俯视图在减少动态效果模式下，对照截图的模型区域像素完全一致。正常动画下逸夫白天图约 0.022% 像素的单通道差值超过 10/255，存在蒸汽等不同时间帧的动态内容；不能声称所有动态帧逐像素相同。
